# Implementation plan: MCP code mode benchmark

This is the working plan for building the experiment in [EXPERIMENT_SPEC.md](EXPERIMENT_SPEC.md).
The spec defines what to measure. This plan defines how to build it and in what order.
If they conflict, the spec wins, except for the deviations listed in section 2.

## 1. How to use this plan

1. Read `EXPERIMENT_SPEC.md` in full, then this file.
2. Find the current milestone in the status table below.
3. Do only that milestone. Meet its exit criteria, update the table, then **stop for human review**.
4. Do not start the next milestone until the human approves.

| Milestone | Scope | Status |
|---|---|---|
| M0 | Project scaffold | Done |
| M1 | Fake data, mock MCP servers, tool tests | Done |
| M2 | 30 tasks, checkers, oracle solutions | Done, awaiting review |
| M3 | Condition A, runner, cache, logging, dry run | Done. Models: `glm-5.3-flash`, `kimi-k2.7-code` |
| M4 | Condition C, sandbox, dry run | Done, awaiting review |
| M5 | Condition B, dry run of all three | Not started |
| M6 | Full run (needs cost approval), analysis, figures | Not started |

M0 is small enough to do together with M1, with one review covering both.

### Hard rules

- **Never call the Opencode Go API** except through `runner.py --dry-run` or a full run the human approved.
  This includes "quick tests". Automated tests use a fake client.
- Never hard-code, log, cache, or pass `OPENCODE_API_KEY` into the sandbox.
- Keep the agents identical except for how tools are exposed.
- Do not change a task, checker, tool, or system prompt after the full run starts. If a change is
  unavoidable, tell the human, because the affected runs must be redone.
- Report results as measured, including results that contradict the source post.

## 2. Deviations from the spec

The spec has a few gaps that would invalidate results if followed literally. Each is resolved as
follows. The human should see these at the first review.

| # | Spec text | Problem | Decision |
|---|---|---|---|
| D1 | Cache key is `hash(model, messages, tools)` | Trials 2 and 3 would replay trial 1, so the 3 trials would be identical and the variance fake | Add `trial` to the key. Rerunning the same trial still hits the cache |
| D2 | `reset` mock state before every run, concurrency 2 | Two concurrent runs sharing state would corrupt each other | Each run gets its own copy of the state (section 4) |
| D3 | Repo root named `mcp-code-exec-experiment/` | The actual directory is `mcp-code-mode-bench/` | Use the actual directory as the root |
| D4 | Metrics list | Cached replays and provider prompt caching would distort latency and token analysis | Add the extra fields `cache_hits`, `cached_input_tokens`, `truncated_outputs`, `stop_reason`, `final_answer` |
| D5 | `GET /models` for IDs, but no API calls outside approved runs | These two rules conflict | Add `runner.py --list-models`. It makes only that GET request and needs human approval the first time, at M3 |
| D6 | Dry run uses 1 task | Tokens vary by orders of magnitude between categories, so one task extrapolates poorly | Keep 1 task, default to a large-data task so the estimate skews high, and label the estimate as rough |
| D7 | Extrapolate "full cost" | The spec gives no prices | Always report tokens and requests. Report money only if optional `PRICE_INPUT_PER_MTOK` and `PRICE_OUTPUT_PER_MTOK` are set |

Dependency: Python 3.11+ is required; pin `requires-python = ">=3.11"` and manage with `uv`.

## 4. Key design decisions

### Tool transport and per-run state

- Servers use the official MCP Python SDK and run over **stdio**, started once per run with
  `MCP_STATE_DIR` pointing at that run's state.
- The base dataset in `data/` is read-only. Before each run, copy only the mutable CRM state to a
  fresh temp directory. Sheets and docs can be read straight from `data/` if no tool mutates them.
- All three conditions reach tools through one MCP client layer, so tool behaviour cannot differ.
- Tool output must be deterministic: IDs come from per-run counters, and no tool reads the wall clock.
  Otherwise messages differ between replays and the cache misses. Use a fixed fake "today" in the data.

### Tool design

32 tools in total: `sheets` 10, `docs` 8, `crm` 14. Built on MCP SDK 2.x (`MCPServer`, not `FastMCP`).
Every tool returns a single compact JSON text block (CSV for `export_sheet_csv`), and `sheets` and
`docs` are read-only.

- Include list, get, search, create, update, and delete operations, with about 5 tools having long,
  realistic descriptions and parameter schemas.
- Keep the same tools for all conditions. Add no tools that exist only to favour one condition.
- **Do not include server-side aggregation** such as `sum_column` or `group_by`. It would remove the
  effect under test.
- `sheets.read_rows(sheet_id, offset=0, limit=None)` returns all rows when `limit` is omitted.
  Models may page in any condition. Record this in the tool description rather than hinting at a strategy.
- Sheets of 50 to 10,000 rows: orders, customers, inventory. At least 3 sheets must have 10,000 rows.

### Final answers

Every condition ends the same way: the model replies with no tool call, and its final message includes
`<answer>...</answer>`. Checkers read that tag and/or the final CRM state. The instruction goes in the
shared system prompt core. Answer parsing and normalisation (numbers, whitespace, list order) live in
`tasks/checkers.py`.

### Shared agent loop

`agents/common.py` holds the loop, and each condition supplies only an object with:

```python
class ToolExposure(Protocol):
    def system_block(self) -> str: ...            # condition-specific prompt block
    def tools(self) -> list[dict]: ...            # OpenAI-format tools for this turn
    async def execute(self, call) -> str: ...     # result text returned to the model
```

The loop stops on a final message, or at 25 model turns (`stop_reason="max_turns"`, `success=false`).

| Condition | Tools sent | Result returned |
|---|---|---|
| A | All ~30 schemas on every request | Verbatim, no truncation |
| B | `search_tools(query)` plus every schema loaded so far | Verbatim, no truncation |
| C | `list_files(path)`, `read_file(path)`, `run_python(code)` | Stdout, truncated to 4,000 chars |

**Condition A oversized results:** do not truncate. If the context exceeds the model's limit and the API
rejects the request, end the run with `success=false` and `error="context_overflow"`. This is a real
outcome of the condition. Do not retry this error.

**Oversized requests that get no clean rejection:** if a request over 500,000 characters times out or
gets a 5xx, end the run after one attempt with `success=false` and `error="oversized_request"`. Retrying
would resend the same payload for the same result. It counts as a failure in success rates, like
`context_overflow`, and `--retry-errors` does not rerun it. Smaller requests still get the normal retries.

**Condition B search:** deterministic BM25 over tool name and description, returning the top 5. No
embeddings and no LLM. The result lists names and one-line summaries, and the full schemas are added to
`tools` from the next request on. Loaded schemas stay loaded for the run.

**Condition C files:** `list_files` and `read_file` are limited to the generated package. Truncated
output ends with a visible marker such as `[output truncated at 4000 chars]`, and the run's
`truncated_outputs` count goes up.

### Sandbox (condition C)

Use Docker. It is available here and enforces the limits properly.

```
docker run --rm --network none --memory 512m --cpus 1 --pids-limit 128 \
  --read-only --tmpfs /tmp --user 1000:1000 --cap-drop ALL \
  -e PYTHONHASHSEED=0 \
  -v <repo>/toolpkg:/toolpkg:ro \
  -v <run_dir>/sock:/sock \
  -v <run_dir>/workspace:/workspace \
  bench-sandbox:<pinned> python /workspace/_submitted.py
```

- `--network none` removes all networking. Wrappers reach tools through `sandbox/gateway.py`, a host
  process listening on a **Unix socket** in the mounted `/sock` directory. It forwards calls to the run's
  MCP client and allows only known tool names. This meets "no network except to the local MCP servers".
- The host enforces the 30-second timeout and kills the container on expiry. Count this as a sandbox
  error, and return the message to the model as the tool result so it can recover.
- The environment passes no API keys, and `.env` is never mounted.
- `/workspace` persists across `run_python` calls within a run, but Python variables do not. State this
  in the condition C block.
- The gateway counts MCP calls, which feed `tool_calls`. `code_executions` counts `run_python` calls.
  `sandbox_errors` counts non-zero exits, timeouts, and out-of-memory kills.
- Tests must confirm: no internet, read-only package, timeout kill, memory kill, and no API key in the
  environment.

### LLM client (`llm.py`)

- Uses the `openai` SDK, reading `OPENCODE_BASE_URL`, `OPENCODE_API_KEY`, and `MODELS` from `.env`.
- Sends `temperature=0`. If a model rejects it, drop the parameter and record this in `run_meta.json`.
- **Cache:** a file per request in `cache/`, keyed by SHA-256 of canonical JSON of
  `(model, trial, messages, tools, params)`. Store the full response and its original latency, but no
  headers or keys. Write atomically (temp file, then rename).
- **Cache hits** use the stored usage and original latency, so a resumed run reports true values, and
  increment `cache_hits`.
- **Tokens** come only from the API `usage` field. If it is missing, log `null` and raise it at the next
  review. Never estimate. Read `prompt_tokens_details.cached_tokens` into `cached_input_tokens` if present.
- **Retries:** on 429 or 5xx, capped exponential backoff with full jitter, max 4 retries, then
  `error="api_error"` and move on to the next run.
- **`--max-requests N`** counts real HTTP requests, including retries, but not cache hits. When reached,
  finish no new requests, do not write a row for the unfinished run, and exit cleanly with a summary.
- **Concurrency:** a global limit of 2 on concurrent runs.

### Runner

```
runner.py --models m1,m2 --conditions A,B,C --tasks all --trials 3 \
          [--dry-run] [--max-requests N] [--retry-errors] [--list-models]
```

- Append one JSON line per finished run to `results/runs.jsonl`, and flush after each line.
- Resume by skipping `(model, condition, task_id, trial)` rows already present. Rows with `error` also
  count as present unless `--retry-errors` is passed, which ignores `api_error` rows only and
  keeps the latest row per key during analysis.
- `--dry-run` writes to `results/dry_runs.jsonl`, not `runs.jsonl`, so it cannot affect the resume logic.
  It still uses the shared cache only under a `dryrun` trial value. It prints tokens per condition, total
  requests, and the extrapolation to 540 runs.
- Write `results/run_meta.json` with package versions, model IDs, Docker image digest, git commit,
  data seed, and start time.

### Log schema

Spec fields: `model, condition, task_id, trial, success, input_tokens, output_tokens, total_tokens,
model_turns, tool_calls, code_executions, sandbox_errors, wall_time_s, timestamp, error`.

Added fields (D4): `cache_hits, cached_input_tokens, truncated_outputs, stop_reason, final_answer`.

Allowed `error` values: `null`, `api_error`, `context_overflow`, `oversized_request`, `max_turns`, `internal`. Define them as
an enum. `internal` means our harness failed: it must be investigated, not analysed as model failure.

## 5. Milestones

### M0: Scaffold

- Run `git init` with a `.gitignore` that excludes `.env` and `cache/`. Commit only when the human asks.
- Create `pyproject.toml` with `openai`, `mcp`, `python-dotenv`, `pytest`, `pytest-asyncio`, `pandas`,
  `matplotlib`, and `rank-bm25`, plus `.env.example` with placeholders.

**Exit:** `uv run pytest` runs with no errors.

### M1: Data and servers

- `data/generate.py` uses a fixed seed and creates the sheets, docs, and CRM base state. Include planted
  facts for later tasks, such as action items in meeting notes and specific matching records.
- Implement the three servers and `servers/state.py`.

**Tests:**
- Running the generator twice gives byte-identical output (compare hashes).
- Every tool has at least one test through a real MCP client session, covering normal and error input.
- CRM writes do not touch `data/` and do not leak between two state directories.

**Exit:** all tests pass. Report the tool count and the character size of the largest tool output and of
the full schema set. Those sizes set the upper bound on what condition A costs.

### M2: Tasks and checkers

- Write 30 tasks: 12 `large-data`, 10 `multi-step`, 8 `simple`.
- Each `tasks.jsonl` row has `id, category, prompt, checker, expected`.
- Each prompt describes a goal in user language. It must not name tools or hint at a strategy.
- Compute expected answers from data in code. Do not type them by hand. Multi-step tasks must use at
  least 3 tools.
- Avoid large-data tasks with a single matching row findable by a search tool, since these would not
  test aggregation. Mix filters, group-bys, joins across sheets, and top-N queries.

**Tests:**
- `tasks/oracle.py` solves each task through the MCP tools with no LLM, and each passes its checker.
- **Negative checks:** each checker rejects a wrong answer, and each state checker rejects the unchanged
  initial state. Without this, a checker that always passes would look fine.

**Exit:** 30 of 30 oracle runs pass and all negative checks fail as intended.

### M3: Condition A, runner, cache, logging

- Implement `llm.py`, `agents/common.py`, `agents/direct.py`, and `runner.py`.
- Use a fake OpenAI client in tests.

**Tests:** cache hit and miss (including different trials missing), backoff and retry cap,
`--max-requests` stop, resume, logging schema, max-turns stop, context overflow handling, and no key in logs or cache.

**Exit:** after human approval, run `--list-models`, set `MODELS`, and run `--dry-run --conditions A`.
Report tokens and the extrapolation, and confirm that the models return `usage` and support tool calls.

### M4: Condition C

- Implement `toolpkg_gen.py`, generating from the live MCP tool list (one module per tool, typed
  signature, docstring from the description). Add a test that fails if `toolpkg/` is stale.
- Implement the sandbox image, gateway, executor, and `agents/code_mode.py`.

**Tests:** sandbox isolation tests (section 4), and the M2 oracle for at least one task per category
rewritten as code that runs through the sandbox.

**Exit:** `--dry-run --conditions C` is reported.

### M5: Condition B

- Implement `agents/tool_search.py` with BM25 search.

**Tests:** ranking is deterministic, loaded schemas persist, and calling a tool that is not loaded returns a clear error.

**Also verify:** diff the three agent files, and confirm the system prompt core is byte-identical across
conditions.

**Exit:** `--dry-run --conditions A,B,C` for all three on one task. Report the estimated full-run tokens,
requests, and cost if prices are set, then **wait for explicit approval**.

### M6: Full run and analysis

Only after the human approves the cost:

1. Run with `--max-requests` in batches. Check for `internal` errors after the first batch, and stop and
   report if any appear.
2. Rerun `api_error` rows with `--retry-errors`, then confirm 540 unique rows.
3. Write `analysis/report.py` to produce everything in spec section 8, with PNGs in `results/figures/`.

**Analysis rules:**
- Answer the spec's question directly: compare A with B for effect (a), and B with C for effect (b).
- Report `context_overflow`, `oversized_request` and `max_turns` as failures. Report any remaining `api_error` or `internal`
  rows separately and exclude them from success rates, stating the count.
- Report token medians both for all runs and for successful runs only, since failed runs may stop early.
- Show the `simple` category separately, since code mode may lose there.
- With 3 trials, show bootstrap confidence intervals on medians and success rates, and avoid claiming
  differences the intervals do not support.
- Note whether provider prompt caching affected tokens, using `cached_input_tokens`.
- Compare the findings with the post's headline claims, stating where they did and did not reproduce.

**Exit:** the report and figures exist and can be regenerated from `results/runs.jsonl` alone.

## 6. Pitfalls to watch

- **`run_meta.json` before M6:** every invocation overwrites it, including dry runs, and
  `temperature_dropped_for` only covers the current process. Fix this before the full run so the file
  describes that run. `kimi-k2.7-code` rejects temperature 0 and runs at its default, while `glm-5.3-flash`
  accepts it, so state that in the report and compare conditions within each model.
- **Cached tokens:** `kimi-k2.7-code` reported no `cached_input_tokens` on S05, so caching may not be
  comparable between the two models.
- **Trial variance:** even at temperature 0, providers may vary. Report what is measured.
- **Tool-call format differences:** models may produce malformed JSON arguments. Return the parse error
  to the model as a tool result, and count it as a normal turn.
- **Parallel tool calls:** a single turn may hold several. Execute all, return all, and count each in `tool_calls`.
- **Task leakage:** the condition blocks must not mention tasks or suggest strategies beyond explaining the interface.
- **Docker startup time** adds to `wall_time_s` in condition C. Measure the overhead of an empty container
  and report it with the latency results. Pre-pull the image before timing.
- **`print` of huge data in C:** truncation handles it, but count these cases for the failure mode table.
